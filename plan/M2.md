# M2 — online play, distribution, mobile (user 2026-10-09)

Decisions and why. The tasks are the M2*/M9*/M13 lines in `plan/TODO.md`.

## Distribution: import the disc in the app, not a builder website

The user's idea: a webpage takes the ISO, strips what the game needs and hands back an executable that no longer
needs the ISO. Keep the second half (strip to a pack, forget the ISO), drop the website that builds executables:

- Server-side would mean uploading 1.4 GB to a server we can't host. Client-side (wasm, File API) works, but
  stitching data into a binary breaks macOS code signatures and Android APK signatures, and iOS can't sideload at all.
- An executable with disc data baked in is a copy of the game anyone can pass around. We ship a clean binary;
  data only ever comes from the player's own disc (AGENT.md).
- Same result, less code: the game imports the disc itself on first start (M13): pick the ISO, check SCUS-97610,
  copy out only what `hst-data` reads into a pack in the user data dir (OPFS in the browser), then the ISO can go.
  The web/PWA build (M9, a static page on GitHub Pages, free) runs the same import in the browser. That page is
  the "website", and it's also how phones get the game (iOS has no other way).

## Netcode

The sim is tick-based and bit-exact (`hst_sim::ps2`), so only inputs go over the wire (`replay::Pad`, 6 bytes per
seat per tick). What stands in the way today (2026-10-09 read of `play.rs`):

1. **Platform floats** (M2a): f32 + − × ÷ and `sqrt` are IEEE everywhere, but std `sin/cos/tan/atan/asin`
   (≈55 calls in `hst-sim`, mostly `camera.rs`) come from each platform's libm. Any of them on a gameplay path
   desyncs x86 vs ARM vs wasm.
2. **Input is read from devices inside the match** (M2b): `read_input` (Update) latches keys/pads into `Pads`,
   `control` consumes them, and `Pads::slot_of` decides who is human from the connected-gamepad count and
   `HST_AUTOPLAY`. Netplay needs "this tick's pads for seats 0–3" from outside, with seats fixed by the lobby.
3. **State is spread out** (M2c): `Game` mixes per-match constants (tables, `Arc<CharacterData>`, collision world)
   with per-tick state; the AI generator is a separate `MatchRng`; `played_out`/`held_ball` read ECS `Motion`/`Rig`;
   ten `play/` modules take `ResMut<Game>`. Lockstep only needs it hashable (desync checks); rollback needs
   snapshot/restore.
4. **Side effects inside the tick** (M2d): sounds, whooshes, cheers, hit effects, jingles are queued by the sim.
   Rollback re-runs ticks, so they'd play twice.
5. **Seeds and setup** (M2e): the AI generator is seeded with a fixed value (P11m1); peers must agree on seed,
   rules, characters, costumes, mods and disc.
6. **Pacing** (M2g): `Time<Fixed>` at 60 Hz runs off the wall clock; netplay ticks run only when every seat's input
   for that tick is in.

Order: delay-based lockstep first (needs 1, 2, 5, 6 and a state hash), rollback after (adds 3's restore and 4).
Tennis timing grades are frame-tight, so rollback is the real target, but lockstep proves determinism with far
less code and stays as the LAN/low-ping mode.

## Hosting and finding games (researched 2026-10-09)

What others do: Fish Folk Jumpy (Rust, `ggrs` rollback) went from matchbox to iroh. matchbox (WebRTC) needs a
signalling server that someone runs. sm64coopdx runs its own CoopNet lobby service. Nobody gets across NATs on the
internet with no server at all: two peers behind home routers need a third party to meet and, for hard NATs, to
relay through. So the aim is "no server **of ours** required, and anyone can host their own".

- **Library: iroh** (QUIC, encrypted, hole punching). One stack for LAN and internet.
- **Discovery: mainline (BitTorrent) DHT**, which belongs to nobody. Use it for address lookup and for the lobby
  list (hosts announce on a fixed key, finders ask each host for its details), instead of n0's DNS service.
- **Relay**: only for traversal when hole punching fails, and always in the browser (no UDP there). n0's free
  public relays by default, a setting for your own `iroh-relay` (one binary, a public IP and a domain), and relays off
  for LAN. A self-hosted relay is the "host it yourself" path.
- **Join by code/QR**: the host's address ticket. Needs no discovery at all, so it's the fallback everywhere.
- **Rollback**: `ggrs` core (not `bevy_ggrs`: our match state isn't plain ECS), its socket trait over iroh
  datagrams, `SyncTestSession` as a CI determinism check.

### LAN, phones included (M2j, M9b)
- Any shared network is a LAN: a router, or one phone's hotspot with no mobile data. mDNS finds lobbies, relays off.
- Native apps only: browsers can't send UDP or do mDNS, and iOS Safari has no Web Bluetooth. Android: sideloaded
  APK, hold a `MulticastLock`. iOS: raw multicast needs an Apple-granted entitlement, so iOS joins by QR/code and
  asks for Local Network permission; shipping on iOS at all needs a developer account (human decision).
- Bluetooth: skipped. No cross-platform peer-to-peer Bluetooth in Rust (btleplug is central-only), none in the
  browser on iOS, and a hotspot already covers "no router around".
- Browser LAN (M2k, maybe): WebRTC with offers swapped by QR code, no server, same network.

## Mods online (possible, M2i)

Gameplay data from a mod (params, scale, reach, AI row, hand) changes the sim, so it always travels in the
handshake. Looks are optional: the first time a remote player uses a mod you don't have, ask once (always / never
/ ask each time). Declined: draw their donor character hue-shifted so it's obviously a stand-in. Mods stay data
only (glb/png/wav/json, checked against the standard's §7, size capped), sent peer to peer.
